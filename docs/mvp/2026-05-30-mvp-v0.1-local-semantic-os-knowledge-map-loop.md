## 1. MVP Goal

Prove that the loop

```
Semantic OS  →  Context Pack (filesystem)  →  Knowledge Map AI  →  2D / 3D + Node Memory + Actions
```

works **end-to-end locally**, with no backend, no database, no AI API call, and
no real Obsidian parser.

The user should be able to:

1. Generate a Context Pack from Semantic OS for a real customer question.
2. Drop the pack into `C:\Drive-semantic\context-packs\…`.
3. Open Knowledge Map AI in a browser.
4. See the pack in the left sidebar.
5. Click it → see the relationship graph (2D / 3D), summary, causality, actions,
   sources, future plan, suggested write-back, and per-node memory.

If that loop works, MVP v0.1 is done.

## 3. C:\Drive-semantic Exchange Layer

`C:\Drive-semantic\` is the **canonical local exchange root** between Semantic
OS (writer) and Knowledge Map AI (reader). Layout:

```
C:\Drive-semantic\
├── context-packs\          ← what Knowledge Map AI reads
│   ├── index.json
│   └── <slug>\<pack-id>\…
├── projection-exports\     ← future
├── action-feedback-inbox\  ← future
├── manifests\              ← future
└── archive\                ← future
```

Knowledge Map AI exposes this directory to the browser via a Windows directory
junction:

```
apps/web/public/context-packs  →  C:\Drive-semantic\context-packs
```

So the browser always fetches `/context-packs/...` — the frontend code does
**not** know about `C:\Drive-semantic`. Setup steps are in
[docs/setup/2026-05-30-context-pack-exchange-setup.md](../setup/2026-05-30-context-pack-exchange-setup.md).

The junction (and its backup) is gitignored — generated exchange artifacts do
**not** live in source control.

## 4. Query Flow

User-facing query flow (manual, no API):

1. User asks a question of Semantic OS (e.g. *"雪红餐馆上次上线出了什么问题？"*).
2. Semantic OS picks a `query_mode` (`incident_root_cause`, `project_status`,
   `summary_review`, …) and generates a Context Pack:
   - `context-pack.json` (graph + summary + causality + actions + future_plan + sources + suggested_write_back + incremental_update)
   - `summary.md`, `actions.md`, `sources.md`
   - `node-memory/<id>.md` for any node with a `memory_file`
3. Semantic OS writes the pack into `C:\Drive-semantic\context-packs\<slug>\<pack-id>\`.
4. Semantic OS appends an entry to `C:\Drive-semantic\context-packs\index.json`
   (with `public_fetch_path`, `query_mode`, `node_count`, `action_count`, …).

## 5. Knowledge Map AI Loading Flow

1. Page mounts → `loadContextPackIndex()` fetches `/context-packs/index.json`.
2. Left sidebar's **DEMO VAULT** renders:
   - the two built-in demos (Accounting Map, Exhibition Map)
   - every entry from the index, each showing a small meta line like
     `incident_root_cause · 11 nodes · 6 actions`
3. User clicks a pack entry → `loadPackByUrl(id, public_fetch_path)`:
   - `loadContextPack(url)` fetches + validates the JSON.
   - `contextPackToGraph(pack)` maps Context Pack node `type` values
     (`Customer`, `Event`, `Problem`, `Conflict`, `Playbook`, `Checklist`,
     `Action`, `Feedback`, `RefactoringNote`, `FuturePlan`, `Source`) to
     dedicated semantic `EntityType`s. **No node is ever shown as
     "Missing Document".**
   - Nodes/edges carry `source_refs`, `evidence`, `confidence`, `created_from`
     into `KnowledgeNodeData` / `KnowledgeEdgeData` for downstream display.
4. The graph is replaced; `ContextPackPanel` opens (Summary / Causality with
   evidence / Actions with `expected_result` + `write_back_target` / Future
   Plan / Sources / Suggested Write-Back / Incremental Update).
5. Click a node → `NodeMemoryPanel` shows summary, confidence badge, `from:` tag,
   evidence, source_refs; if the node has a `memory_file`, the markdown is
   lazy-fetched from `/context-packs/<slug>/<pack-id>/node-memory/*.md`.
6. The 2D / 3D toggle is always available; selecting a node never resizes the
   canvas (the panel is an overlay on desktop, a bottom sheet on mobile).

## 6.1 Local Private vs Public Demo Mode

MVP v0.1 is a **local private** product. The loop described above runs on a
private developer / customer machine that has populated
`C:\Drive-semantic\context-packs\`.

The same source code also ships in **Public Demo Mode** on `map.clawshow.ai`,
where the Context Pack pipeline is *intentionally hidden*:

- Public Demo Mode (default, when `NEXT_PUBLIC_ENABLE_CONTEXT_PACKS` is not
  `"true"`): the sidebar shows only the two built-in sanitized demos
  (Accounting Map, Exhibition Map). The app does not fetch
  `/context-packs/index.json` and never references private pack ids.
- Local Private Mode (`NEXT_PUBLIC_ENABLE_CONTEXT_PACKS=true` in
  `apps/web/.env.local`): the full Semantic OS → Knowledge Map AI loop is
  active.

The Golden Test Packs below all live in Local Private Mode. They must **not**
appear in production deployments. See
[docs/setup/2026-05-30-context-pack-exchange-setup.md](../setup/2026-05-30-context-pack-exchange-setup.md#public-demo-mode-vs-local-private-mode)
for the rules.

## 7. What is Intentionally NOT Included in v0.1

- ❌ No backend / API / server route to query Semantic OS.
- ❌ No database.
- ❌ No real AI call from the frontend.
- ❌ No real Obsidian / Markdown parser inside Knowledge Map AI.
- ❌ No customer login / multi-tenant separation.
- ❌ No write-back execution (suggested write-backs are *displayed*, not applied).
- ❌ No automatic refresh of the index — the page reads it once on mount.
- ❌ No production deploy of generated Context Pack data — `C:\Drive-semantic` is
  local-only. `https://map.clawshow.ai` does **not** currently see these packs.
- ❌ No ontology UI controls. Ontology stays internal to the adapter.
- ❌ No selected-node-only relationship space in 3D (rejected after testing).

## 8. Next Engineering Priorities (post-v0.1)

In rough order, not committed:

1. **Sync / deploy strategy for Context Packs** — figure out how production
   `map.clawshow.ai` will see packs generated locally (e.g. publish a tagged
   pack bundle into the deploy artefact, or sync a read-only subset).
2. **Obsidian / Semantic OS read adapter (Phase 2)** — let Knowledge Map AI
   ingest a vault directly (scan folders, parse `[[wikilinks]]`, tags,
   frontmatter) so it can build a graph without a pre-generated pack.
3. **Action write-back execution** — turn "suggested_write_back" into a real
   action that updates the Semantic OS markdown files (still local-first).
4. **Incremental update / merge across packs** — when a new pack about the same
   target arrives, merge instead of replace.
5. **Long-lived knowledge graph view** — aggregate across all loaded packs for a
   single customer / project, not just per-pack.
6. **Quality dashboard** — surface `confidence`, `evidence` coverage, and
   `source_refs` health across the vault.
